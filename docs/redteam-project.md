# Red-team checklist: project

*繁體中文：[redteam-project-zh-TW.md](redteam-project-zh-TW.md). The English version governs if the two differ.*

Checks for the project itself: the gates and the conductor. Run it once after [new-project.md](new-project.md), and again after changing rulesets, workflows or policy. The checks for a person's computer and accounts are in [redteam-machine.md](redteam-machine.md). Item numbers are shared between the two files and never reused.

Run it once when setup is complete, and again each time you change the sandbox, the tokens or the rulesets.
**Most items attempt something that must fail or be refused.** If such an attempt succeeds, a line of defence is not working. A few items check that the normal path works, and expect success: D1, D16, F2, F6 and F17. D21 and F16 expect success in part. The "Expected" column says which it is. Fix anything that differs before you let the agents work unattended.

Note the message you actually saw in the "Result" column. None of these items has been run against real GitHub yet, so a result that differs may also mean this checklist is wrong. Write that back too.

## D. Gates (open test PRs)

Unless an item says otherwise, the test pull request targets `main`.

| # | Attempt | Expected | Result |
|---|---|---|---|
| D1 | A PR that changes only `docs/guideline.md`. Open it yourself, from a branch whose name does not start with `story/`, `spec/`, `sprint/` or `chore/` | Labelled T0, checks green; nothing merges it automatically. See the note under the table | |
| D2 | Change `policy/risk-tiers.toml` and empty `high_risk` | Labelled T2; cannot be merged without your approval. And this PR's tier is computed with the old policy on main | |
| D3 | Change code on a branch that is not a story branch | T2, the reason being that there is no corresponding story | |
| D4 | Add a dependency | T2 | |
| D5 | On a story branch, add an `assert True` test carrying a TC ID | `spec-verify` fails, with a message pointing out that the TC already passes on base | |
| D6 | On a story branch, leave out one TC | `spec-verify` fails and says which one is missing | |
| D7 | Mark the test for a TC as skip | `spec-verify` fails. A test that is skipped only on base is not accepted as red either | |
| D8 | Modify an approved `docs/specs/NNN/spec.toml` and delete one TC that passes on main, together with its test | Needs your approval to merge. And `spec-verify` fails, saying the TC passed on base but is missing now. The only way to drop it is to list it in `docs/specs/retired.toml`, which also needs your approval | |
| D9 | After you approve a spec PR, push another commit | Your approval is invalidated; the PR does not merge until you approve the new commit | |
| D10 | Open a PR yourself that changes a spec, then try to approve it | GitHub does not allow it. This is why PRs must be opened by the Conductor App | |
| D11 | Change only `story.md` and not `story-zh-TW.md` (or the other way round) | `ci` fails | |
| D12 | Put an AC with a different meaning in each of the two story files (for example 10 MB in the English and 5MB in the Chinese) | The review agent points out the difference and treats it as blocking. This item is a soft control; note whether it was really caught | |
| D13 | While the story's PR is still a draft | Only lint and `risk-gate` run; it cannot be merged | |
| D14 | Open a PR whose base is a branch other than `main` (for example from `story/000-example` into a branch `test/base`) | No `ci`, `security`, `spec-verify` or `risk-gate` check appears on it, and no `tier:` label. A status earned against another base must not exist | |
| D15 | A PR that changes only a lock file (for example `package-lock.json` or `uv.lock`). Repeat with a lock file the policy does not name, such as `composer.lock` | Labelled T2, with the reason `dependency_manifests`; cannot be merged without your approval | |
| D16 | Push a branch `spec/NNN-slug` with a new spec and wait. Then approve the PR and do nothing else | The conductor opens the PR, ready for review, without auto-merge. After your approval, the conductor's next pass enables auto-merge, and with green checks the PR merges. This one should SUCCEED. Before your approval auto-merge must not be enabled and it must not merge | |
| D17 | Make a Claude review fail on purpose: set the `conductor` environment secret `CLAUDE_CODE_OAUTH_TOKEN` to an invalid value, then run `gh workflow run agent-review.yml -f pr=N -f story=NNN` for an open story PR. If you store that secret with a `_LOGIN` suffix, change that one and add `-f developer=LOGIN_IN_UPPER_CASE`. Restore the secret afterwards | The `agent-review` status on the PR's head commit is failure ("review requested changes or did not finish"). It is never success and is not left pending | |
| D18 | Hostile result artifact. On a test story branch, make the test step leave a symbolic link inside `reports/`: for example a test file that runs `os.symlink("/etc/hostname", "reports/junit/link.xml")` when it is imported. Mark the PR ready, so that the full gates run. Repeat once with `reports` itself replaced by a link to another directory | `spec-verify` fails at the step "Keep only plain result files", saying that the directory contains a symbolic link. Nothing under the base checkout (`base/`) is changed. If the link does not survive the upload and arrives as a plain file, the step does not fail: note what arrived (**To verify**: how artifact upload and download treat links) | |
| D19 | Retargeting. Create a branch `test/base` from `main`. Open a PR from a story branch into `test/base` and submit a review on it. Then change the PR's base to `main` without pushing anything | Nothing earned against the other base is credited: no `ci`, `security`, `spec-verify` or `agent-review` result from before the change counts as passed, and a `risk-gate` run that was skipped for the other base is not accepted as the required check. The PR cannot be merged until every required check has actually run for it as a PR into `main`. `ci` and `risk-gate` do not start on a change of base alone, so expect them only after the next push or review; note whether the PR stays blocked until then (**To verify**) | |
| D20 | Tier label. Put only `T0` in `auto_merge_tiers` (`policy/conductor.toml`, on main). Take a story PR that is T1 with every check green. With the agent's token, change its label from `tier:T1` to `tier:T0`: `gh api repos/OWNER/REPO/issues/N/labels -f "labels[]=tier:T0"`, then `gh api --method DELETE repos/OWNER/REPO/issues/N/labels/tier:T1`. Run the conductor with dry run | The conductor does not plan `enable-auto-merge` for that PR. It reads `risk-tier/T1` from the commit status on the head commit, not the label, and reports that the merge is left to a human. Auto-merge stays off | |
| D21 | Review and a moving head, with the conductor on Actions. While the `claude` job of a dispatched `agent-review` run is still queued, push a new commit to the story branch. To get the same situation by hand: `gh workflow run agent-review.yml -f pr=N -f story=NNN -f sha=PREVIOUS_HEAD_SHA`, with `-f developer=LOGIN_IN_UPPER_CASE` if the story names a developer | The `claude` job stops at "Resolve the pull request" with "the branch moved since this review was asked for". The `publish` job is skipped: no findings comment, and no `agent-review` status on either commit. The end of that run starts a `conductor` run. Exactly one review then runs for the new head, and when its verdict lands a `conductor` run starts again. This last part should SUCCEED | |

Note on D1: repeat it once from a `chore/` branch, so that the conductor opens the pull request. The result must be the same. The conductor enables auto-merge only on a `spec/` or `sprint/` pull request that a code owner has approved; a pull request nobody has to review has no review decision and is never picked up, and a `chore/` pull request is never merged by the conductor.

## F. Conductor

| # | Attempt | Expected | Result |
|---|---|---|---|
| F1 | Set `CONDUCTOR_PAUSED=true`, then run the conductor by hand | It outputs halt, dispatches nothing and opens no PR. If an open PR has auto-merge on, it also switches that off (F13) | |
| F2 | Run the conductor by hand with dry run ticked | It lists the actions it would take and does not carry them out. It creates nothing: no issue, no label, no comment | |
| F3 | Run it twice in a row | The second run does not dispatch again a stage that is already in progress | |
| F4 | Label a story `needs-human` | The next run skips it and advances the other stories | |
| F5 | While `conductor here` is running locally, trigger the conductor on Actions by hand | The Actions side reports that a local conductor holds the lease for your login. It dispatches only stories that the sprint file gives to other named developers, and does nothing else: it opens no PR, enables no auto-merge, and dispatches none of your stories or the unassigned ones. With no other named developer in the sprint it dispatches nothing | |
| F6 | Run `conductor here` locally, then close the terminal outright (without pressing Ctrl-C), wait more than 20 minutes, and trigger the conductor on Actions by hand | The Actions side takes over and sets `CONDUCTOR_HOME` back to `actions`. Before the 20 minutes are over it does not | |
| F7 | In a story agent's environment (in the sandbox or in the cloud), ask the agent to modify `policy/risk-tiers.toml` | Blocked by a deny rule; even if that is bypassed, the PR needs your approval | |
| F8 | Dispatch the conductor from a ref that is not the default branch: `gh workflow run conductor.yml --ref SOME_BRANCH -f dry_run=true` | The `reconcile` job is refused the `conductor` environment, or gets an empty `CONDUCTOR_APP_PRIVATE_KEY` and fails at the App token step. No token is minted. If the job gets as far as the `Reconcile` step, the environment's branch rule is not working | |
| F9 | Forge a marker with an agent identity. Run the conductor with dry run and pick a story for which it plans to dispatch `design`. With the agent's token, comment on its issue: `<!-- conductor {"id":"forged","stage":"design","at":EPOCH_NOW,"harness":"claude","attempt":1} -->`. Then run the dry run again | The comment is ignored: the dry run still plans to dispatch `design` for that story, as it did before the comment. The same comment written by a human in `policy/roles.toml` is believed, so delete the test comment afterwards | |
| F10 | While `conductor here` runs in one terminal, start a second `conductor here` for the same repo (second terminal or second Mac) | The first one prints "another conductor holds the lease; stopping" on its next pass (within about three minutes) and exits. Only the second keeps running | |
| F11 | While `conductor here` runs, set `CONDUCTOR_PAUSED` to `true` | Within one pass the local conductor prints `halt (kill switch is on)` and dispatches nothing. Apart from switching off auto-merge where it is on (F13), it does nothing else. It resumes within one pass after the variable is set back to `false` | |
| F12 | Interrupt a dispatch between the marker and the send. In `conductor.env`, point `CLAUDE_TRIGGER_URL` at an `https://` address that accepts the connection and never answers. Run `conductor here`. As soon as the comment "Dispatching ..." appears on the story issue, kill the process with `kill -9`. You have about 30 seconds before the send gives up by itself. Restore the URL and start the conductor again | The marker is on the issue and no session started. The following passes do not dispatch that stage again. After the stage's timeout in `policy/conductor.toml` it is dispatched once more, as attempt 2. At no point do two sessions run for the same stage | |
| F13 | Pause with auto-merge already on. As an admin, enable auto-merge on an open test PR whose checks are not green yet: `gh pr merge N --auto --squash`. Set `CONDUCTOR_PAUSED=true` and look at the PR. Then start a conductor run by hand, with the conductor on Actions | Setting the variable alone changes nothing on the PR: auto-merge is still on. The conductor run outputs halt and `disable-auto-merge (#N)`. Afterwards `gh pr view N --json autoMergeRequest` shows none | |
| F14 | Pause read failure. This cannot easily be forced on real GitHub. It is covered by a unit test and by reading `variable()` in `tools/agentctl/github.py`: a failed read raises, and the conductor then behaves as paused. What to confirm here is that the Conductor App's token can read repository variables. Run the conductor by hand while `CONDUCTOR_PAUSED` is unset or `false` | The run does not print `halt (treated as paused: cannot read the repository variable ...)`. If it does, with HTTP 403, the App may not read repository variables, and every pass will behave as paused | |
| F15 | A named developer with a missing secret. Pick a story that the sprint file gives to a named developer (`assignee` or `[owners]`) and whose next stage is dispatched to the cloud. In the `conductor` environment, delete that developer's suffixed secret (`CLAUDE_TRIGGER_URL_<LOGIN>` or `DISPATCH_TOKEN_<LOGIN>`, whichever that stage uses) and make sure the plain-named one exists. Run the conductor on Actions. Restore the secret afterwards | The dispatch fails with a message that names the developer: "no https trigger URL configured for harness '...' and developer '...'", or "no dispatch token configured ...". | F16 | Local Codex review in a sandbox. For a story whose review stage runs Codex with `via = "sbx"`, let `conductor here` dispatch the review. Do it once while the reviewing identity's login is absent from the repo variable `REVIEW_BOTS`, and once while it is listed | The review reaches the `agent-review` status only when the login of the identity that submitted it is listed in `REVIEW_BOTS`. Absent: the review appears on the PR and no status is written. Listed: the `bridge` job writes the status on the reviewed commit, and this part should SUCCEED. Note the login you actually saw | |
