# Threat model

*繁體中文：[threat-model-zh-TW.md](threat-model-zh-TW.md). The English version governs if the two differ.*

Each row is a class of incident that has really happened or can be expected, mapped to the controls that stop it. Controls are of two kinds. **Hard** controls are enforced by the environment or by GitHub, and the agent cannot get round them. **Soft** controls can be bypassed and serve only as a second layer. The design behind the controls is in [guideline.md](guideline.md); the column "Layer" says which layer's checklist tests the control.

The numbers are stable: a number that was withdrawn (17's lease, 28's Lima case, 37) is not reused, and a row that changed keeps its number. Where a control is marked **To verify**, it follows documentation or reasoning and has not been run on real GitHub, Docker Sandboxes or a Mac (see [the guideline](guideline.md#11-verified-and-not-yet-verified)).

## Assets

| Asset | Worst case | Recoverable? |
|---|---|---|
| Private data on the Mac | Read and taken into a vendor's context, or sent outside | No |
| Files on the Mac outside the working directory | Deleted or overwritten | From backup |
| Temporarily valid cloud CLI tokens | Used to operate on cloud resources while they are valid | Depends on the operation |
| The repository's history and main | Rewritten, or faulty code merged in | Yes (git), but at a high cost |
| The guardrails themselves (workflows, `agentdev.toml`, specs) | Once weakened, the other lines of defence fail | Yes, provided someone notices |
| The installed kit on the Mac, and the kit version a project pins | Replaced, so that code of an attacker's choice runs on the Mac or in the judges | Yes, if noticed; the Mac may already be compromised |
| The conductor's credentials (the Conductor App's key, dispatch secrets) | Used to open, approve-by-merge or dispatch as the pipeline | Revocable; damage done meanwhile is not |
| The subscription accounts' login state | Stolen | Can be revoked |
| Future production and databases | Deleted or leaked | No |

## Threats and controls

|---|---|---|---|---|
| 1 | 1 | The agent reads private files under home | The microVM mounts only the project repository, read-only; cloud sessions are not on your machine | Harness deny rules (`agentctl harness-settings`); the project's guard hook |
| 2 | 1 | The agent deletes files outside the working directory by mistake (`rm -rf ~/`) | As above: those files are not in the VM | Guard hook; the project is not kept in a directory synced by iCloud; backups |
| 3 | 1 | The agent uses cloud credentials on the machine | Directories such as `~/.aws` do not exist in the VM | Deny rules block the cloud CLIs |
| 4 | 1 | Prompt injection (repository content, issues, web pages, package descriptions) induces the agent to send data out | Egress allowlist on top of a deny-all network preset, probed from inside each sandbox when it is created (#40); the VM holds no secrets worth sending out, apart from the subscription login state. This assumes the project directory holds none (#32) | Rule 7 of the project's `AGENTS.md` (repository content is data) |
| 5 | 2, 3 | The agent installs a malicious or non-existent package (slopsquatting, compromised packages) | A change to a manifest or lock file in `[risk.t2] dependency_manifests` is always T2 and needs human approval to merge; installation happens inside the VM; the egress allowlist limits calls back out | Rule 5 of the project's `AGENTS.md`. Not covered: the list is one the project must extend for its own stack; a manifest it does not name is not T2 |
| 6 | 2 | The agent pushes straight to main, force-pushes or deletes branches | Ruleset `main` (layer 2): main can only be changed through a pull request. Ruleset `main-merge`: only admins and the Conductor App may update main (**To verify**). The agent acts as a GitHub App with only the permissions it was granted and no bypass | Guard hook; deny rules |
| 7 | 2, 3 | The agent modifies CI to make the checks pass | The agent token has no Workflows permission; `.github/**` and the scanner configuration are guardrails (CODEOWNERS and T2), as is `agentdev.toml`; the judging checks run the kit at the pinned SHA with the settings of the base branch; only pull requests into main are judged; changed paths are read with `git diff -z`, so a path git would otherwise quote still matches the patterns | Rule 3 of the project's `AGENTS.md` |
| 8 | 2, 3 | The agent weakens the risk rules or the kit version | The risk rules and the pin are in `agentdev.toml`, a guardrail that is always T2; the prompts and tools are not in the project at all, they are in the installed kit at the pinned SHA (#46, #47) | As above |
| 9 | 3 | The agent claims to have written tests but has not, or has written empty tests | `spec-verify`: traceability (based on execution results) and red-green | The review agent's faithfulness audit. | 10 | 3 | The agent modifies or deletes tests to suit the implementation | Specs are protected by CODEOWNERS; a TC that has passed in any of up to five recent `ci` runs on main may not disappear, even when its spec is deleted in the same change, unless a human lists it in `retired.toml`; red-green, in which a test skipped on base or a base run with no report does not count as red, and neither does a base run whose setup command failed, or a test missing from a base report in which no failure belongs to the story's own test files (these last two rest on files written by the job that ran the pull request's code; see #21) | The review agent checks, one by one, every test change made after the tests stage |
| 11 | 2 | The agent quietly changes the requirements | The specs, sprints and product documents are in CODEOWNERS and T2; a new push invalidates earlier approvals | |
| 12 | 1, 2 | The agent approves or merges its own pull request | The agent's GitHub App cannot be a code owner; pull requests are opened by the Conductor App; the App cannot approve; the `main-merge` ruleset keeps an agent's token from merging (#34) | Deny rules block `gh pr merge` |
| 13 | 3 | The agent forges the `agent-review` result | The agent token has no commit status permission; the status is written by a `publish` job that never sees the pull request's files; the verdict is written outside both checkouts and counts only if the review step succeeded, otherwise the status is failure; the reviewer runs in a checkout of the default branch with a read-only token, so its settings and hooks do not come from the pull request; the tool list of the reviewer is restricted (**To verify**); required checks (ruleset `main-checks`, layer 3) must be reported by GitHub Actions (**To verify**) | None against the reviewer being talked into a wrong verdict by the text it reviews. See guideline section 6: this is the weakest link, and the hard guarantees do not depend on it |
| 14 | 2 | The agent deploys or creates a release on its own | Ruleset `release-tags`: only an admin can create, move or delete `v*` tags; the project's release job (its own file, from the template) requires the checks present and green on the tagged commit; the cloud trusts only OIDC that comes from a tag; there are no long-lived keys | |
| 15 | 2 | The agent deletes the production database or its backups | The agent and CI have no production credentials; the deploy role has no permission to delete backups; migrations are T2 (`high_risk`) | |
| 16 | 3 | A secret is committed | gitleaks in the `security` check | Rule 6 of the project's `AGENTS.md` |
| 17 | 4 | The conductor runs away: endless retries, opening pull requests in bulk | Daily pull request limit, limits on retries, fix rounds and triage, the work-in-progress limit, stage timeouts; the kill switch `CONDUCTOR_PAUSED`, read live on every pass and taken as on when it cannot be read (#43); a dispatch is recorded before it is sent, so an interrupted pass does not send it twice; a lock file allows one conductor per project per Mac; after three failed passes in a row the conductor waits 15 minutes between passes | Daily brief. Not covered: a second conductor on another Mac (#48) |
| 18 | 4 | The agent drifts from its instructions after running for a long time | There are no long sessions: each stage is a fresh context, and the state lives on GitHub | |
| 19 | 3, 4 | Behaviour changes after a model upgrade | Scheduling is deterministic code; the gates are mechanical checks | Weekly audit sampling |
| 20 | 1 | Computer use, browser extensions or personal-data connectors touch private data | None. These paths do not go through the VM | Rule: do not turn them on. See guideline section 4 |
| 21 | 3 | The agent writes a fake test results file directly and fools `spec-verify` | None. The test results are produced by the pull request's code in the first place | The files `test_cmd` runs are reviewed like any code; the review agent; weekly spot checks |
| 22 | 3 | The two versions of a bilingual story differ in meaning | Matching structure and changing both together are enforced by `spec-lint` | The PO's own comparison; the review agent compares them item by item |
| 23 | 3 | A pull request's code leaves something behind on a shared, long-lived runner that holds logins: it changes the firewall, reads the logins or persists into later jobs | No self-hosted runner is part of the kit. `overflow_runner` is empty by default, so `ci` and `security` run on GitHub-hosted runners; the jobs that pass judgement never move, whatever is configured | None once you configure an overflow runner: nothing checks that it is dedicated, credential-free and recreated for every job |
| 24 | 2 | A maintenance session is induced to weaken the guardrails | Changes to guardrail paths always need human approval to merge | Rule 3 of the project's `AGENTS.md`: only something a human asks for directly in the session counts as a maintenance request |
| 25 | 3 | The Actions allowance is exhausted and the gates cannot run | When the allowance runs out, pull requests cannot be merged; nothing is merged without the gates | Usage estimate in the daily brief. Overflow is off, so nothing relieves it automatically: merging stops until the next month or until you pay for more |
| 26 | 1 | The agent plants a git hook or edits `.git/config` in a mounted repository, and it runs on the Mac the next time you use git there | Clone mode: the repository is mounted read-only and the agent works on a private clone | `agentctl doctor --inside` warns when the workspace is writable |
| 27 | 1 | The agent uses your forwarded SSH agent to push as you, bypassing its own identity | `agentctl sandbox setup` turns SSH agent forwarding off; outbound SSH is not on the allowlist | `agentctl doctor --inside` fails when an SSH agent with keys is reachable |
| 28 | 1 | The agent's GitHub credential is stolen from inside the sandbox | Neither the App's key nor a long-lived token is in the VM; the proxy on the host injects a one-hour token | The token is valid for an hour and can be revoked in the App's settings |
| 29 | 1 | An agent acts outside its role: a reviewer or triage agent changes code, or pulls in packages | Its token is minted without push permission and its sandbox cannot reach the package registries (`tools/agentctl/profiles.py`); a sandbox is never reused, so it cannot inherit another stage's network rules. Sandbox path only | The stage prompt; the harness deny rules |
| 30 | 1 | An agent widens its own privileges by editing the token profiles or the sandbox scripts on its branch | These are part of the installed kit, outside the project and read-only, and the launcher takes the version from the default branch (#46) | |
| 31 | 1, 4 | Code from a pull request or from an agent's branch runs on the Mac or in a judging job: a file named like a module (`agentctl.py`, `json.py`) in the current directory, or the branch's version of a host script | There is no host code in the project tree. The launcher and `tools/run.py` start the kit with `python3 -I`, which keeps the current directory and `PYTHONPATH` off the import path; the conductor reads specs and settings from a fresh worktree of `origin/main`; the judges run the kit at the pinned SHA; story id, stage and harness are validated before they reach a path, a sandbox name or a command | None needed: the former check that a checkout is trusted is gone with the code it protected |
| 32 | 1 | A secret in the project directory is read by an agent: clone mode mounts the whole directory read-only, ignored files included | None for a file you put there yourself. The pipeline's own credentials are read from outside the repository: `~/.config/agent-dev/<owner>-<repo>/conductor.env` and `~/.config/agent-app/`. The shared skills store is turned off (**To verify**) | `sbx.sh` refuses to start a sandbox while an untracked file, ignored or not, has a name that looks like a secret. It goes by file name and can be overridden. Rule: keep nothing secret in the project directory |
| 33 | 2, 3 | A workflow that holds credentials runs in the version of itself found on a branch | Credentials are secrets of the `conductor` environment, which only the default branch may use, so a run from any other ref gets none (**To verify**); no workflow that holds them is triggered by a push to a branch; the Claude reviewer runs only when dispatched from the default branch; the agent token has no Workflows permission | The environment and its branch rule are created by hand during setup. A secret created as a repository secret instead is not protected this way |
| 34 | 1, 2 | An agent opens, retargets or merges a pull request with its own token | Opening, retargeting and reviewing: the token that pushes has pull requests: read. Merging is a different control: GitHub's merge endpoint needs only contents: write, which that token has, so what stops the merge is the `main-merge` ruleset, which lets only admins and the Conductor App update main; the `main` ruleset has no bypass (**To verify**: narrowing the token, and the layering of the two rulesets). Sandbox path only | Deny rules block `gh pr create`, `gh pr review` and `gh pr merge`. Not covered: the review token can write to pull requests, although it cannot push or merge; a cloud session acts as the account you connected |
| 35 | 4 | An agent forges a conductor marker comment to fake a dispatch, cancel one or silence a notification | Markers are believed only when written by the conductor's own login or by a human listed in `[roles]`, read from the default branch | None. A person whose login equals the Conductor App's slug would be believed too; that person would have to be a collaborator to comment at all |
| 36 | 3, 4 | A stale or wrong pull request is taken for the story's: a closed one, one into another base, one from a fork | The conductor picks only the open pull request, else the merged one, from this repository into the default branch, and only from the branch name the spec defines (`story/NNN-slug`); a fix, a conflict resolution and a review are tied to the commit they were dispatched for, and every new commit needs its own verdict; the review workflow refuses a pull request that is not open, same-repository and into the default branch; `ci` and `security` run only for pull requests into main; `risk-gate` fails, and is not skipped, for a pull request into another base, because GitHub counts a skipped job as a passed required check; a pull request retargeted to main without a push has no `ci`, `security` or `spec-verify` result and stays blocked until the next push (**To verify**) | |
| 38 | 3 | A hostile result artifact redirects files into the judge's checkout: the job that ran the pull request's code leaves a symbolic link in `reports/`, and unpacking follows it | `spec-verify` unpacks the artifact in the runner's temporary directory, outside both checkouts; only plain `*.xml` files and `collected.json` are passed on; a symbolic link anywhere in it fails the job; the base branch, which supplies the judge's settings, is checked out last (**To verify**: how `actions/download-artifact` behaves with a hostile archive) | None. | 39 | 4 | An agent edits the `tier:` label on a pull request so that a higher-tier change is auto-merged | The conductor reads the tier from the commit status `risk-tier/*` that `risk-gate` writes on the head commit, not from the label; the agent token has no commit status permission; several statuses may be present: the strictest wins, which can only make the conductor more cautious, and none found means T2; only statuses described as "pull request #N into BRANCH" for this pull request and the default branch count; auto-merge is enabled only for the commit the decision was made about (`--match-head-commit`); a T2 change also keeps `risk-gate` red until a human approves (**To verify**: the statuses appearing in `statusCheckRollup`, and `--match-head-commit`) | The label remains, for people only. ## Reference incidents

The types of public incident consulted during design, used to check the table above for gaps:

- An agent deleted a production database after being explicitly asked to stop making changes (July 2025, Replit and SaaStr). Corresponds to #14, #15.
- An agent deleted a database and its backups through a cloud platform's API (reports from April 2026). Corresponds to #3, #15.
- A compromised npm package instructed the local AI CLIs to search for secrets and send them out, in the mode that skips permission prompts (August 2025, the Nx incident). Corresponds to #1, #4, #5.
- A model produced the name of a package that did not exist, and the name was then registered as a malicious package. Corresponds to #5.

The details of the last three items come from secondary reports and were not checked one by one against the primary sources.

## Out of scope

- Malicious insiders. The people on the project are trusted.
- A compromised Mac. If a process runs as you on the Mac that runs the conductor, it can read the conductor's key and change the installed kit. The kit limits what agents can reach; it does not protect a host that is already hostile.
- Data handling on the vendors' side. What is sent to the models is governed by each vendor's terms.
- A compromise of GitHub itself, or of Docker Sandboxes' isolation. The sandbox is assumed to hold; its network filter is spot-checked (#40), nothing more.
