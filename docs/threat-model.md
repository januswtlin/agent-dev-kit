# Threat model

*繁體中文：[threat-model-zh-TW.md](threat-model-zh-TW.md). The English version governs if the two differ.*

Each row is a class of incident that has really happened or can be expected, mapped to the controls that stop it. Controls are of two kinds. **Hard** controls are enforced by the environment or by GitHub, and the agent cannot get round them. **Soft** controls can be bypassed and serve only as a second layer.

## Assets

| Asset | Worst case | Recoverable? |
|---|---|---|
| Private data on the Mac | Read and taken into a vendor's context, or sent outside | No |
| Files on the Mac outside the working directory | Deleted or overwritten | From backup |
| Temporarily valid cloud CLI tokens | Used to operate on cloud resources while they are valid | Depends on the operation |
| The repo's history and main | Rewritten, or faulty code merged in | Yes (git), but at a high cost |
| The guardrails themselves (workflows, policy, specs) | Once weakened, the other lines of defence fail | Yes, provided someone notices |
| The subscription accounts' login state | Stolen | Can be revoked |
| Future production and databases | Deleted or leaked | No |

## Threats and controls

| # | Threat | Hard controls | Soft controls |
|---|---|---|---|
| 1 | The agent reads private files under home | The VM mounts only the project directory, read-only; cloud sessions are not on your machine | `denyRead` in `.claude/settings.json`; guard hook |
| 2 | The agent deletes files outside the working directory by mistake (`rm -rf ~/`) | As above: those files are not in the VM | Guard hook; the project is not kept in a directory synced by iCloud; backups |
| 3 | The agent uses cloud credentials on the machine | Directories such as `~/.aws` do not exist in the VM | Deny rules block the cloud CLIs |
| 4 | Prompt injection (repo content, issues, web pages, package descriptions) induces the agent to send data out | Egress allowlist on top of a deny-all network preset, probed from inside each sandbox when it starts (#40); the VM holds no secrets worth sending out, apart from the subscription login state and, in the Lima fallback, the agent token. This assumes the project directory holds none (#32) | AGENTS.md rule 7 |
| 5 | The agent installs a malicious or non-existent package (slopsquatting, compromised packages) | A change to one of the manifests and lock files listed in `policy/risk-tiers.toml` is always T2 and needs human approval to merge: common manifests, any `*.lock`, `*.lockb`, `*.lockfile`, `*.sum` or `*.resolved`, and registry configuration such as `.npmrc` and `pip.conf`; installation happens inside the VM; the egress allowlist limits calls back out | AGENTS.md rule 5. Not covered: the list is one the project must extend for its own stack; a manifest it does not name is not T2 |
| 6 | The agent pushes straight to main, force-pushes or deletes branches | Ruleset `main`: main can only be changed through a PR. Ruleset `main-merge`: only admins and the Conductor App may update main (**To verify**). The agent acts as a GitHub App with only the permissions it was granted and no bypass | Guard hook; deny rules |
| 7 | The agent modifies CI to make the checks pass | The agent token has no Workflows permission; `.github/` and the scanner configuration (`.gitleaks.toml`, `.semgrepignore` and the like) are in CODEOWNERS; the judging checks are run by the base branch's copy of the tools, with its policy, started as `python3 -I`; only PRs into main are judged; changed paths are read with `git diff -z`, so a path git would otherwise quote still matches the policy patterns | AGENTS.md rule 3 |
| 8 | The agent weakens the risk rules, prompts or tools | `policy/`, `prompts/` and `tools/` are in CODEOWNERS and are T2 | As above |
| 9 | The agent claims to have written tests but has not, or has written empty tests | `spec-verify`: traceability (based on execution results) and red-green | The review agent's faithfulness audit. It is also the only thing that catches a test written to behave differently on main than on the branch (for example by checking whether a file exists): red-green shows that the story's tests do not pass on main, and tests are PR code |
| 10 | The agent modifies or deletes tests to suit the implementation | Specs are protected by CODEOWNERS; a TC that has passed in any of up to five recent `ci` runs on main may not disappear, even when its spec is deleted in the same change, unless a human lists it in `docs/specs/retired.toml`; red-green, in which a test skipped on base or a base run with no report does not count as red, and neither does a base run whose setup command failed, or a test missing from a base report in which no failure belongs to the story's own test files (these last two rest on files written by the job that ran the PR's code; see #21) | The review agent checks, one by one, every test change made after the tests stage |
| 11 | The agent quietly changes the requirements | `docs/specs/` is in CODEOWNERS; a new push invalidates earlier approvals | |
| 12 | The agent approves or merges its own PR | The agent's GitHub App cannot be a code owner; PRs are opened by the Conductor App; the App cannot approve; the `main-merge` ruleset keeps an agent's token from merging (#34) | Deny rules block `gh pr merge` |
| 13 | The agent forges the `agent-review` result | The agent token has no commit status permission; the status is written by a `publish` job that never sees the PR's files; the verdict is written outside both checkouts and counts only if the review step succeeded, otherwise the status is failure; the reviewer runs in a checkout of the default branch with a read-only token, so its settings and hooks do not come from the PR; `--tools` limits the tools the reviewer has (**To verify**); required checks must be reported by GitHub Actions (**To verify**) | None against the reviewer being talked into a wrong verdict by the text it reviews. See the explanation in guideline 4: this is the weakest link, and the hard guarantees do not depend on it |
| 14 | The agent deploys or creates a release on its own | Tag ruleset: only an admin can create `v*`; the release job requires `ci`, `security` and `spec-verify` to be present and green on the tagged commit; the cloud trusts only OIDC that comes from a tag; there are no long-lived keys | |
| 15 | The agent deletes the production database or its backups | The agent and CI have no production credentials; the deploy role has no permission to delete backups; migrations are T2 | |
| 16 | A secret is committed | gitleaks in the `security` check | AGENTS.md rule 6 |
| 17 | The conductor runs away: endless retries, opening PRs in bulk | Daily PR limit, limits on retries and fix rounds, WIP limit; the kill switch, read live on every pass by the Actions job and by the local conductor, and taken as on when it cannot be read (#43); a dispatch is recorded before it is sent, so an interrupted run does not send it twice. Two conductors that overlap around a hand-over can still duplicate a dispatch; each re-reads the lease before every dispatch, which narrows this but does not close it | Daily brief |
| 18 | The agent drifts from its instructions after running for a long time | There are no long sessions: each stage is a fresh context, and the state lives on GitHub | |
| 19 | Behaviour changes after a model upgrade | Scheduling is deterministic code; the gates are mechanical checks | Weekly audit sampling |
| 20 | Computer use, browser extensions or personal-data connectors touch private data | None. These paths do not go through the VM | Rule: do not turn them on. See guideline 3 |
| 21 | The agent writes a fake test results file directly and fools `spec-verify` | None. The test results are produced by the PR's code in the first place | `Makefile` is protected by CODEOWNERS; the review agent; weekly spot checks |
| 22 | The two versions of a bilingual story differ in meaning: the Chinese you approved and the English the agent implements do not match | Matching structure and changing both together are enforced by `spec-lint` | The PO's own comparison; a review agent from the other vendor compares them item by item |
| 23 | A PR's code leaves something behind on the self-hosted runner that affects later jobs | Overflow is off by default (`overflow_runner = []`), so `ci` and `security` run on GitHub-hosted runners; the jobs that pass judgement never move, whatever is configured | None once you configure an overflow runner: nothing checks that it is rebuilt for every job. See #37 |
| 24 | A maintenance session is induced to weaken the guardrails | Changes to guardrail paths always need human approval to merge | AGENTS.md rule 3: only something a human asks for directly in the session counts as a maintenance request |
| 25 | The Actions allowance is exhausted and the gates cannot run | When the allowance runs out, PRs cannot be merged; nothing is merged without the gates | Usage estimate in the daily brief. Overflow is off by default, so nothing relieves it automatically: merging stops until the next month or until you pay for more |
| 26 | The agent plants a git hook or edits `.git/config` in a mounted repository, and it runs on the Mac the next time you use git there | Clone mode: the repository is mounted read-only and the agent works on a private clone | `agentctl doctor --inside` warns when the workspace is writable |
| 27 | The agent uses your forwarded SSH agent to push as you, bypassing its own identity | `sandbox/sbx.sh setup` turns SSH agent forwarding off; outbound SSH is not on the allowlist | `agentctl doctor --inside` fails when an SSH agent with keys is reachable |
| 28 | The agent's GitHub credential is stolen from inside the sandbox | With sbx neither the key nor the token is in the VM; the proxy on the host injects a one-hour token | In the Lima fallback the key is in the VM; revoke it in the App's settings |
| 29 | An agent acts outside its role: a reviewer or triage agent changes code, or pulls in packages | Its token is minted without push permission and its sandbox cannot reach the package registries (`tools/agentctl/profiles.py`); a sandbox is never reused, so it cannot inherit another stage's network rules. Docker Sandboxes path only | The stage prompt; the harness deny rules |
| 30 | An agent widens its own privileges by editing the profiles or the sandbox scripts on its branch | Sandboxes are set up by a copy of the tooling pinned outside the repo and by the scripts on the default branch | Those paths are guardrails: CODEOWNERS and T2. `sandbox/sbx.sh` refuses to run from a checkout whose host scripts differ from the default branch (#31) |
| 31 | Code from a PR or from an agent's branch runs on the Mac or in a judging job: a file named like a module (`agentctl.py`, `json.py`) in the current directory, or the branch's version of a host script | `bin/agentctl`, the CI judges and the token helpers start the tooling as `python3 -I tools/run.py`, which keeps the current directory and `PYTHONPATH` off the import path; the judges run the base branch's copy; sandboxes are set up by a copy pinned outside the repo; the local conductor starts sandboxes with the scripts of a fresh checkout of `origin/main`; story id, stage and harness are validated before they reach a path, a sandbox name or a command | `sandbox/sbx.sh` and `agentctl conductor here` refuse to run when `sandbox/`, `tools/`, `bin/` or `policy/` differ from the default branch. This guards against the accident of running them from an agent's branch. The check is part of those scripts, so it does not stop a checkout that is already hostile. Rule: run host scripts from a clean checkout of the default branch |
| 32 | A secret in the project directory is read by an agent: clone mode mounts the whole directory read-only, ignored files included | None for a file you put there yourself. The pipeline's own credentials are read from outside the repo: `~/.config/agent-dev/<owner>-<repo>/conductor.env` and `~/.config/agent-app/`. The shared skills store is turned off (**To verify**) | `sandbox/sbx.sh` refuses to start a sandbox, or to re-attach to one, while an untracked file, ignored or not, has a name that looks like a secret (`.env*`, `*.pem`, `*.key`, `.npmrc` and similar). It goes by file name and can be overridden. Rule: keep nothing secret in the project directory |
| 33 | A workflow that holds credentials runs in the version of itself found on a branch | Credentials are secrets of the `conductor` environment, which only the default branch may use, so a run from any other ref gets none (**To verify**); no workflow that holds them is triggered by `pull_request` or by a push to a branch: `notify.yml` has no permissions and no secrets, and the conductor reacts to it through `workflow_run`; the Claude reviewer runs only when dispatched from the default branch; the agent token has no Workflows permission | The environment and its branch rule are created by hand during setup. A secret created as a repository secret instead is not protected this way |
| 34 | An agent opens, retargets or merges a PR with its own token | Opening, retargeting and reviewing: the token that pushes has pull requests: read (`tools/agentctl/profiles.py`). Merging is a different control: GitHub's merge endpoint needs only contents: write, which that token has, so what stops the merge is the `main-merge` ruleset, which lets only admins and the Conductor App update main; the `main` ruleset has no bypass (**To verify**: narrowing the token, and the layering of the two rulesets). Docker Sandboxes path only | Deny rules block `gh pr create`, `gh pr review` and `gh pr merge`. Not covered: the review token can write to PRs, although it cannot push or merge; a cloud session acts as the account you connected |
| 35 | An agent forges a conductor marker comment to fake a dispatch, cancel one or silence a notification | Markers are believed only when written by the conductor's own login or by a human listed in `policy/roles.toml`; `roles.toml` is read from the default branch | None. Not covered: a cloud session acts as your account, which is a listed human, so a marker it writes is believed. A person whose login equals the Conductor App's slug would be believed too; that person would have to be a collaborator to comment at all |
| 36 | A stale or wrong PR is taken for the story's PR: a closed one, one into another base, one from a fork | The conductor picks only the open PR, else the merged one, from this repository into the default branch, and only from the branch name the spec defines (`story/NNN-slug`); a PR into another base does not count as the branch's PR, so the real one is still opened; a fix, a conflict resolution and a review are tied to the commit they were dispatched for, and every new commit needs its own verdict; the review workflow refuses a PR that is not open, same-repository and into the default branch; `ci` and `security` run only for PRs into main; `risk-gate` fails, and is not skipped, for a PR into another base, because GitHub counts a skipped job as a passed required check and the result would stay on the commit after a retarget; a PR retargeted to main without a push has no `ci`, `security` or `spec-verify` result and stays blocked until the next push (**To verify**) | |
| 37 | PR code runs on a shared, long-lived runner that holds logins: it changes the firewall, reads the logins or persists into later jobs | Overflow is off by default, so `ci` and `security` do not run on the Lima VM's runner; that runner is not part of the supported setup path | None once you set `overflow_runner`: the policy file says the runner must be dedicated, credential-free and recreated for every job, and nothing enforces it |
| 38 | A hostile result artifact redirects files into the judge's checkout: the job that ran the PR's code leaves a symbolic link in `reports/`, and unpacking follows it | `spec-verify` unpacks the artifact in the runner's temp directory, outside both checkouts; only plain `*.xml` files and `collected.json` are passed on; a symbolic link anywhere in it fails the job; the base branch, which supplies the judge, is checked out last (**To verify**: how `actions/download-artifact` behaves with a hostile archive) | None. Not covered: the content of the files that are passed on is still whatever the PR's job wrote (#21) |
| 39 | An agent edits the `tier:` label on a PR so that a higher-tier change is auto-merged | The conductor reads the tier from the commit status `risk-tier/*` that `risk-gate` writes on the head commit, not from the label; the agent token has no commit status permission; the status is on a commit, not on a PR, so several can be present: the strictest found wins, which can only make the conductor more cautious, and none found means T2; auto-merge is enabled only for the commit the decision was made about (`--match-head-commit`); a T2 change also keeps `risk-gate` red until a human approves (**To verify**: the statuses appearing in `statusCheckRollup`, and `--match-head-commit`) | The label remains, for people only. An agent's token has issues: write and can still change it |
| 40 | The sbx network preset is no longer deny-all after setup, or a sandbox that already exists keeps wider rules than its stage allows | None. The preset is machine-wide, and nothing in this repo pins it or reads back the rules of a running sandbox | `sandbox/sbx.sh` makes up to three requests from inside the sandbox on every creation and on every re-attach of an interactive sandbox. `https://github.com/`, which is on the allowlist, must answer 2xx or 3xx; otherwise "refused" cannot be told from "no network" and the script stops with "cannot check". Then `https://example.com/`, and for a stage that does not build `https://registry.npmjs.org/`: a 2xx or 3xx answer means reachable and the script refuses; no answer, or a 4xx or 5xx answer (taken to be the proxy answering in the host's place), counts as refused. A missing `curl` or a failed `sbx exec` is "cannot check"; `AGENT_SKIP_NETWORK_PROBE=1` overrides "cannot check" only; the remaining requests are still made. The marker left by `setup` is a convenience. Not covered: this is a spot check of three hosts, not a proof that the effective allowlist equals the project's lists; a change made while a sandbox is attached; a re-attach relies on the `curl` inside a sandbox an agent has already used (**To verify** on a real machine: what a request denied by the sbx proxy looks like from inside, and that `github.com` is reachable) |
| 41 | A review verdict is published for a commit other than the one the conductor asked about, or a second review runs for the same request | The conductor passes the commit recorded in the dispatch marker (`sha`); if the PR's head is a different commit when the job starts, the job fails before reviewing and nothing is published; the status is written on the commit that was reviewed, and every new commit needs its own verdict (#36); the completion of `agent-review` wakes the conductor, which asks again for the new head (**To verify**: `workflow_run` on `agent-review`) | None. Not covered: a push that lands after that check, while the review runs. The verdict is then on the older commit, and the new head still needs its own. For a review started by a comment or run in a local sandbox, the prompt names the commit and tells the reviewer to stop if the head differs; that is an instruction to an agent, not an enforcement like the workflow's check |
| 42 | A named developer's story silently runs on another person's credentials | For a story whose sprint file names a developer, only `NAME_<LOGIN>` is used (`secret` in `tools/agentctl/github.py`); the plain `NAME` is used for stories of `default`, and on a developer's own Mac for that developer's stories; a missing secret makes the dispatch fail before anything is written, and on Actions that includes the review token; the review workflow uses only `CLAUDE_CODE_OAUTH_TOKEN_<LOGIN>` for a named developer, so a review sent by a local conductor, which cannot see GitHub's secrets, fails in the review step and gets a failure status; a local conductor defers other developers' stories | None. Not covered: nothing checks that the value stored under `NAME_<LOGIN>` really is that person's credential |
| 43 | A kill switch that cannot be read is taken as "not paused"; or auto-merge that is already switched on carries on after a pause | Repository variables are read through the API, and a failed read raises instead of reading as unset; `CONDUCTOR_PAUSED`, `CONDUCTOR_BOT` and `CONDUCTOR_QUOTA` are read first and together, and if any cannot be read the pass behaves as paused and still withdraws auto-merge; on Actions, if the lease variables cannot be read, or the lease is fresh but names no developer, the run dispatches nothing and still handles halt and the withdrawal; a paused pass switches off auto-merge on every open PR that has it on, and so does an Actions run that finds a fresh local lease (**To verify**: `gh pr merge --disable-auto` as the Conductor App) | Rule: for an immediate stop, also run `gh pr merge NUMBER --disable-auto` by hand. Not covered: "dispatching has stopped" is not "auto-merge has been withdrawn". The second needs a pass that could list the PRs and call GitHub successfully, and it happens when a conductor next runs, not when the variable is set; a PR whose checks turn green before that is still merged by GitHub. If GitHub's API is failing altogether nothing can be withdrawn, and the manual command is the fallback |
| 44 | Auto-merge stays armed on a PR across a later push, so GitHub merges a commit that nobody decided about | GitHub still requires all five required checks on the new commit; `risk-gate` fails a T2 commit until a human approves; on every pass the conductor withdraws auto-merge from a story PR that no longer meets what it was enabled for (not a draft, no human review outstanding, the four mechanical checks and `agent-review` green, tier in `auto_merge_tiers`) and enables it again when it qualifies (**To verify**: that GitHub keeps the request across a push, and the withdrawal) | None. Not covered: the window between a push and the conductor's next pass, in which the request is still armed. What it can let through is a commit of a tier above the enabled ones but below T2 (T1 while only T0 is enabled) that also passes `ci`, `spec-verify` and `agent-review` before the conductor runs |
| 45 | A check that was skipped on a draft PR is counted as passed | A draft cannot be merged; marking it ready (`ready_for_review`) triggers a full run of `ci`, `security` and `spec-verify` on the same commit (**To verify**: that the fresh runs replace the skipped results before the PR becomes mergeable) | |

## Reference incidents

The types of public incident consulted during design, used to check the table above for gaps:

- An agent deleted a production database after being explicitly asked to stop making changes (July 2025, Replit and SaaStr). Corresponds to #14, #15.
- An agent deleted a database and its backups through a cloud platform's API (reports from April 2026). Corresponds to #3, #15.
- A compromised npm package instructed the local AI CLIs to search for secrets and send them out, in the mode that skips permission prompts (August 2025, the Nx incident). Corresponds to #1, #4, #5.
- A model produced the name of a package that did not exist, and the name was then registered as a malicious package. Corresponds to #5.

The details of the last three items come from secondary reports and were not checked one by one against the primary sources.

## Out of scope

- Malicious insiders. The two developers are trusted.
- Data handling on the vendors' side. What is sent to the models is governed by each vendor's terms.
- A compromise of GitHub itself.
